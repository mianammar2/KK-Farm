# D-039: Reference reader is the Chainway C72; Android bridge to the web app
2026-11-07 · Status: **Proposed** · Answers Q-RF-1, Q-RF-2 (partly), Q-RF-3 in [OPEN_QUESTIONS.md](../OPEN_QUESTIONS.md); relates to D-028

## Context
The project lead supplied photos of the farm's test readers. From the About screens: model **C72**, Android 13, MediaTek MT6765V/CB (8 cores), 4 GB RAM, 64 GB, 1080×1920, build `C72.AD13.GL.20250303.V1.12`, DeviceAPI `ver20241230`, Chainway app 3.1.5, Zebra 2D barcode engine, Wi-Fi + dual-SIM 4G. The pistol-grip unit with an RF-wave antenna panel is a UHF (EPC Gen2) reader. AnyConfig 1.09 and CDM 1.29 are Chainway's config tools. Device serial numbers, IMEIs and MACs appear in the photos and must stay out of the repository.

## Decision
- The reference reader is the Chainway C72 (UHF EPC Gen2). Tags are assumed UHF until a tag is inspected (Q-RF-2 stays open for the tag brand and EPC format).
- Integration uses the **Chainway DeviceAPI** (not Zebra's SDK). The SDK is vendor-supplied; check its licence before committing binaries, otherwise keep it out of Git and document setup.
- The web app stays a PWA (D-028). A small native Android component on the C72 reads tags and hands them to the PWA. Order of preference: (1) keyboard-wedge / broadcast intent configured in AnyConfig, for the first spike; (2) a thin Kotlin bridge or Capacitor wrapper calling DeviceAPI directly, for single-tag mode, power and RSSI control.
- Action flows (move, treat, weigh) require a **single-nearest-tag mode** (low power, RSSI threshold, one result per trigger). Inventory mode (many tags) is used only for pen counts and compares the scanned set with the expected set.
- The hardware-agnostic scan interface from RFID_INTEGRATION_RESEARCH.md §4 is unchanged: the app resolves `tag_code → open rfid_assignment → animal`.

## Consequences
- First hardware spike: print the trigger key codes, read an EPC, and run a single-tag read against real tags.
- Barcode/QR scanning (Zebra engine) can identify pens, silos and medicine bottles; the camera supports photo records.
- Android 13 background limits mean scanning runs in a foreground context and sync uses a constrained background job.
- D-036's "no live hardware" restriction needs an explicit owner decision before the spike (see Open items in CLAUDE.md).

## Spike result (2026-11-07, on the real C72 over wireless adb)
- **Reading works out of the box through Chainway InfoWedge** (`com.rscja.infowedge`, a DataWedge-like service). The trigger broadcasts `com.rscja.android.KEY_DOWN/KEY_UP`; InfoWedge runs the UHF read (DeviceAPI R2000) and then broadcasts **`com.rscja.android.DATA_RESULT`** with extras `data` (String: the EPCs read, **one per line**) and `overwrite` (Boolean), followed by `com.rscja.android.OVER_RESULT`. Its default profile also emits keystrokes, which only land when a text field has focus.
- Real EPCs are 24 hex characters, for example `E280699500004000FD384063`. One trigger pull at default power read 1 to 4 tags in a room, so **multiple reads per pull are normal**: single-tag mode (lower power, RSSI) is still needed for action flows.
- No vendor SDK was needed for this. The `android/` app (`com.kkfarm.scanner`, Kotlin WebView) listens for `DATA_RESULT`, opens `/scan?tag=CODE` for one tag, and shows a "which goat?" chooser when several are read. Verified on the device: a single real EPC opened the Goat Register with the code filled in; the two-tag read showed the chooser.
- Connection during the spike: the app loads `http://localhost:8000` through `adb reverse`, so the laptop's server is never exposed on the farm Wi-Fi. Standalone use needs a reachable server (Wi-Fi LAN address, or the future hosted SaaS over HTTPS).
- Still open: InfoWedge power/RSSI settings for nearest-tag reads, trigger behaviour when the app is in the background, a signed release build, and kiosk/auto-start on the gun.
- **Read range (2026-11-07):** InfoWedge Profile0 shipped at **30 dBm** antenna power (maximum) and read up to 10 tags across the room per pull. With the owner's approval it was lowered to **10 dBm** (range 5 to 30 dBm, InfoWedge → Profile0 → Configure RFID settings → Antenna transmit power). Other RFID settings left as found: filter duplicates on, ETSI 865–868 MHz, read duration unlimited, separator `\n`, output EPC in hex, keystroke output on, intent output off (InfoWedge's own intent action `com.infowedge.data` / extra `data_string` is available if `DATA_RESULT` ever changes). The right power for ear tags in a crowded pen still needs a field test.
- **InfoWedge can die silently (2026-11-07).** InfoWedge (`com.rscja.infowedge`, system uid) crashed with a NullPointerException in `ProfileDetailActivity.refreshPreferences` (`Profile.isEnable()` on null) when its settings screen was resumed after being left open in the background. The whole reading service died and nothing restarted it for 10 minutes: the trigger did nothing. Settings changed in its UI were also lost because they had not been saved before the crash. Rules: always leave InfoWedge with Back, never switch away from its settings screen. Mitigation in the app (v0.2.1): while KK Farm is on screen it starts `com.rscja.infowedge.SERVICE` (exported `WedgeService`) every 20 s, which restarts the reader if it died.
- The antenna power was re-applied as 10 dBm after the crash and InfoWedge was left with Back so it persists. AnyConfig (`com.rscja.anyconfig.user`) can also push configuration to the gun; for a fleet, the RFID profile (power, output) should be set once in AnyConfig/CDM rather than by hand on each gun.
